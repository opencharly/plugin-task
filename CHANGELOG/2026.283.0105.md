# 2026.283.0105 — fix(git-submodules): a bump reconciles the submodule own nested checkouts (plugin-task#11)

## Summary

Closes opencharly/plugin-task#11. `charly task sync` advances each submodule's gitlink but did not
touch that submodule's **own initialized nested checkouts**, so they stayed at the gitlinks the old
commit recorded: the shared tree went dirty (` M box/arch` … ` M marketplace`) and the R7 gate
(`charly task verify`) then failed **twice over** — the umbrella's own checkout audit (`charly: dirty
working tree`) and its nested half (`FAIL: charly nested submodules not at their gitlinks`) — on a change
the sync itself had just made.

**The fix** (`candy/plugin-task/verbs.go`): `pinSubmodule` already detached the submodule to the ref and
staged the gitlink in the superproject; it now also calls `reconcileNestedCheckouts`, which brings that
submodule's own nested checkouts back onto the gitlinks its new commit records. Guarded twice, and both
guards are load-bearing:

- a submodule with **no `.gitmodules`** is untouched — a plain file test, so no git call and no network
  for the majority of submodules;
- the update is `git submodule update --recursive` **without `--init`**: it moves the nested checkouts
  that are *already initialized* (exactly the ones the issue reports going stale) and never grows the
  checkout. `--init` would fetch nested remotes on every bump — including file-protocol fixtures, which
  would then need a protocol loosening this verb must not bake in — and a bump is not the place to grow
  a checkout. The recursion stays because a nested checkout can itself nest.

A reconcile that cannot complete is a **hard error**, not a warning: a bump that leaves the tree dirty
is worse than a bump that refuses.
