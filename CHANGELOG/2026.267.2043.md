# 2026.267.2043 — feat: the generic declarative task runner (kind:task, command:task, verb:task)

## Summary

Introduce `opencharly/plugin-task` — the generic declarative **task runner** for
charly, the replacement for a Taskfile. It provides three capabilities:

| Capability | Surface | Purpose |
|---|---|---|
| `kind:task` | a `task:` node in `charly.yml` | a named, host-native, reusable plan using the same `#Step`/`#Op` grammar a candy's `plan:` uses |
| `command:task` | `charly task [list] [<name>] [--dry-run] [--json] [--param k=v] [--all]` | run a task (and its `depends_on` closure) on the host |
| `verb:task` | a `task:` verb step in a plan | compose a declared task into a candy/box/task plan |

**No new execution engine.** It reuses the SDK's existing plan machinery — the
same the check engine uses:

- `kit.RunPlan` walks the plan; a task grammar over `checkkit.PlanGrammar`
  supplies do-mode/context resolution (a task is host-native, so its steps run
  unconditionally in authored order).
- `checkkit.VerbResolver` dispatches each step's verb through the host provider
  registry over the reverse channel (`InvokeProvider`), so a task can use any
  verb, any plugin verb, `include:` composition, and `agent-*` steps.
- `kit.ShellExecutor{}` is the host venue; `dir:` is applied by chdir around the
  sequential walk and restored after.

The `kind:task` entity body is the base-schema `#Task` (added in
opencharly/spec#153, merged + tagged `v0.2026267.834`), validated host-side
against `#TaskValue` — a task's `plan: [...#Step]` references the base grammar,
which a self-contained plugin schema cannot carry. The plugin's deep
`OpValidate` supplies the CONCRETE gate the closedness-only host value gate
cannot express (missing `description`, empty `plan`).

This repo's Go module pins the shared `github.com/opencharly/sdk
v0.2026266.1111` and `github.com/opencharly/spec v0.2026267.834` — the same
contract pins charly's in-tree modules use (the `tools/gomod-canonical` gate).

Full Go-Task parity: `description`, `dir` (`${VAR}`/`$VAR` expand against vars,
resolved params, and the process env), `env`, `vars`, `depends_on`, `sources`,
`generates`, `status`, `preconditions`, `silent`, `interactive` (refuses to run
without a real TTY), `platforms`, `exclude_platforms`, `timeout`, `continue_on_error`,
`params` (declared defaults overlaid with `--param`; `required: true` enforced),
and the ordered `plan:`.

### The in-repo R10 gate — the changed path executes live

`command:task` needs the **compiled-in** placement (it reads the host's loaded
project over the reverse channel; an out-of-process CLI has none — the same
documented behaviour as `candy/plugin-clean`). So the gate that actually
exercises the change is **`scripts/gate-task.sh`**, run by `.github/workflows/deploy.yml`:
it fetches charly pinned to **`v2026.267.1938`** (the tag carrying the generic
host-value-gated kind seam `#TaskValue` → `spec.KindValueDefs` + the
`foldHostValueGatedKind` dispatch arm), compiles `candy/plugin-task` INTO that
binary, then drives `charly task` end to end. Against an older charly the `task:`
node fails `"no input def registered"`, so the gate is sensitive to the seam.
