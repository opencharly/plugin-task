# 2026.278.0508 — fix(prune): never sweep through an uninitialized submodule — git -C walks up to the superproject (#16)

## Summary

`verb:prune` swept the **SUPERPROJECT** once for every **present-but-uninitialized** submodule — and in `mode=prune` its Pass 2 reached `git branch -D` on the project's own branches, including **other sessions'** (rule 9).

`pruneRepos` accepted a submodule directory when it merely *existed*. `git -C <path>` only CHANGES DIRECTORY, so on an uninitialized submodule directory — an empty dir, the normal state of a fresh `git worktree` before `git submodule update --init` — git WALKS UP to the enclosing repository and resolves to the superproject. Every git call the sweep made through that path (`worktree list`, `for-each-ref`, `branch -D`) therefore read and MUTATED the *project itself*: its own worktrees and branches surfaced once per uninitialized submodule, and Pass 2 deleted them.

This is the exact defect class **#8 fixed for `verb:git-submodules`** (charly#768); it was never applied to `verb:prune`. The walk-up-safe guard already exists in this repo — `submoduleAt` (`verbs.go:303`).

Changes:
- `candy/plugin-task/prune.go` — `pruneRepos` now includes a submodule only when `submoduleAt` succeeds. An uninitialized submodule contributes **nothing**, so the sweep is strictly smaller, never larger — the direction the verb's own doc promises ("unavailable ⇒ prunes strictly LESS, never more").
- `candy/plugin-task/prune_test.go` — `TestPrune_UninitializedSubmoduleIsNeverSwept`: asserts `pruneRepos` excludes the uninitialized submodule AND that a `mode: report` run attributes no target to it. **FAILS on the pre-fix code; passes on the fix** (both pasted below).
- `scripts/gate-task.sh` — **two** changes. (1) The gate is **repaired so it builds and runs at all**: `CHARLY_TAG="${CHARLY_TAG:-v2026.267.2313}"` → `CHARLY_REF="${CHARLY_REF:-main}"` (with the clone line, the echo and the PASS line), the five fixtures' retired `version:` keys dropped, and `export CHARLY_PLUGIN_ONLY=1` added to the setup region — the fixes for findings F1 and F2 of the verdict (RCA below). (2) It gains **section 4**: a fixture with a declared-but-uninitialized submodule, asserting (a) no target is attributed to it, (b) the project's own target is still reported (the guard must not disable the sweep), (c) `mode=prune` completes cleanly with the unmerged branch kept, the merged one reaped and the uninitialized dir intact.
- `README.md` — the `prune` contract says "every submodule"; it now says every **initialized** checkout, and why.

Closes #16.

**The `WARNING: charly is a dev/worktree build …` lines are root-caused — and they are a real defect in this gate: its output is not reproducible between hosts.** One such line prints **per charly process** (~20 in a full run), and it appears **only when the host actually has the charly package installed**.

Mechanism, from the source (`charly/charly/plugin_loader.go:482-495`): `bakedPluginDirs()` calls `warnSkippedFHSPlugins()` whenever `!packagedInstall()`; a dev/worktree binary deliberately does **not** load `/usr/lib/charly/plugins` (those plugins were built against a different charly — issue #328), and the warning makes that skip *visible* instead of silent. `$CHARLY_PLUGIN_ONLY=1` returns **before** that call — it is the documented "resolve AS-IF-UNPACKAGED" mode, and it is the semantically correct setting for a gate whose entire point is to run *this tree's* plugin.

Proven A/B against a dev build — **stdout identical, exit 0 both ways**, so the variable changes the notice and nothing else:

```
$ env -u CHARLY_PLUGIN_ONLY <dev charly> version 2>a.err >a.out; echo exit=$?
exit=0
$ grep -c 'NOT loading the installed' a.err
1
$ CHARLY_PLUGIN_ONLY=1 <dev charly> version 2>b.err >b.out; echo exit=$?
exit=0
$ grep -c 'NOT loading the installed' b.err
0
$ diff a.out b.out && echo stdout-identical
stdout-identical
```

So the warnings are **eliminated rather than explained**: this PR adds `export CHARLY_PLUGIN_ONLY=1` to the gate's setup region, with that reasoning as a comment beside it. The committed run pasted below therefore prints **zero** warning lines — a count of 0, not an assertion of 0. The variable is also what makes the gate's output comparable between machines at all.
