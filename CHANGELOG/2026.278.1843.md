# fix(prune): force a worktree removal when it holds a populated submodule; skip locked worktrees

## Summary

`charly task prune` (`MODE=prune`) **FAILED the whole step** — `1 step(s), 1 failed`, exit 1 — on a worktree holding a **populated submodule**, and because the failure returns `spec.StatusFail` the Pass-2 branch reap never ran, so `feat/<slug>` survived. MEASURED on a real umbrella session worktree:

```
$ ./charly/bin/charly task prune --param MODE=prune
task prune: 1 step(s), 1 failed
  [fail] run — prune merged-upstream worktrees and branches across the umbrella + submodules
      prune: remove worktree <session-worktree-path>: git worktree remove (exit 128)
charly: error: command "task": task "prune" failed (1 step(s) failed)
```

**RCA — `git worktree remove` refuses for THREE independent reasons, and prune handled ONE.** Enumerated from clean fixtures before naming any cause (R1):

| # | Refusal | git's message | Pre-fix handling |
|---|---|---|---|
| 1 | untracked entries | `contains modified or untracked files, use --force` | **HANDLED** — force keyed on the untracked count |
| 2 | populated submodule | `working trees containing submodules cannot be moved or removed` | **UNHANDLED** — raised even when the worktree is **CLEAN** |
| 3 | locked | `cannot remove a locked working tree; use 'remove -f -f'` | **UNHANDLED** — and a *different* remedy |

Signature 2 is the **routine** umbrella case, not an edge case: reading a skill by path (R0) populates `marketplace`, a build populates `charly` — exactly the sessions `prune` exists to reap. The discriminating bound is measured: a submodule that is **declared but NEVER initialized removes fine**, so only a *populated* one blocks.

Signature 3 is a **separate** finding with a **different** remedy: a lock is deliberate operator protection, and a single `--force` does not even clear it (`-f -f` is required, MEASURED). Forcing would both violate the intent and still fail the step, so it must be **skipped**.

### The fix

- **Force** when the worktree holds a populated submodule: `force = untracked > 0 || populatedSubmodules(wt) > 0`.
- `populatedSubmodules` counts entries in the **worktree gitdir's own `modules/` directory**. The predicate is deliberately **NOT** `git submodule status`'s leading character: MEASURED (git 2.56.0), a submodule initialized and then **DEINITIALIZED** still reports `-` (so it *looks* uninitialized) yet **still** refuses removal, because its gitdir survives `deinit`. Only a never-initialized submodule removes fine — exactly the case with no `modules/` directory. A `submodule status`-based predicate would have mis-classified the deinitialized case and left this bug live.
- **Skip** a locked worktree before the merge check, naming the lock.
- **Disclose** both forces in the report (`discards N populated submodule(s)`), so a force is never silent — the same discipline the existing untracked arm already applies.

### Tests — 4 new, each guarding its own premise against git's measured behaviour

- `PopulatedSubmoduleWorktreeReaped` — the regression: pre-fix this failed the step and the branch survived.
- `NeverInitializedSubmoduleWorktreeReaped` — the no-over-force arm, asserted on the target's **OWN** report line (a whole-message match would hit a sibling worktree's disclosure).
- `DeinitializedSubmoduleWorktreeReaped` — pins the subtlety that forced the `modules/`-directory predicate.
- `LockedWorktreeSkipped` — the lock must survive prune.

Each asserts the premise FIRST (a clean submodule-bearing worktree **is** refused without force; a never-initialized one **is** accepted), so the test fails if git's behaviour ever changes rather than silently passing.

Closes #18
