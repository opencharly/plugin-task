# 2026.297.2006 — feat(task): a task's resolved values reach a step's process environment as DATA

## Summary

A task's `params:` reach a plan step only as **text**: the expander substitutes the value into the step's command, and the shell then PARSES that text — so a value that is DATA becomes SOURCE, and a `$(…)` inside a value EXECUTES with the step's privileges. This change opens the second channel. The task's resolved values — its `vars`, its `env`, its resolved `params` and `TASK_DIR` — are handed to the SDK as `kit.RunnerConfig.StepEnv`, so they reach every step as the step's **process environment**, where the shell never re-parses them. The change is 7 files, +401 −45 (Head `253120997a33e1c021fb7c88609a78ef84f8b1de`).

Closes #34.

Three rules bound the channel, and each is a rule the SDK's own merge already owns, so the plugin adds no second implementation of any of them:

- the step's OWN `env:` WINS a name collision — the author spoke last about their own step, and the task's value is a default;
- a name the shell cannot export (outside `[A-Za-z_][A-Za-z0-9_]*`) is REJECTED and RETURNED, and the SDK renders it as a NOTE on the step's message ("not exported (not a valid shell identifier): …") — disclosed, never dropped silently;
- a piped stdin is not a resolved value, so it is NOT exported. The map is CLONED before `captureStdin` mutates it, because the command verb renders an exported value into the command TEXT, and a NUL byte (a piped binary stream carries one) would make the exec un-runnable. The stream keeps its own channel: `TASK_STDIN` / `TASK_STDIN_FILE` stay reachable through the text expansion they have always had.

A lowercase param is a second, independent win: the expander's grammar is uppercase-only, so a lowercase param was previously unreachable from a step at all. The environment is what makes it reachable BY NAME.

### RCA

- **Mechanism:** the task engine had exactly ONE route from a resolved value to a step — the expander, which substitutes the value into the command TEXT. A shell parses the text it is given, so the value is re-parsed on the way: a `$(…)` inside it EXECUTES, and a `;` or a space splits it into words. The value changed from DATA into SOURCE at the moment it crossed that channel.
- **Missed control:** nothing asserted that a value stays DATA. The expander's contract was "the value's TEXT is substituted", and there was no second channel, so the only way to reach a step was the unsafe one; and the suite asserted what a step's command RECEIVED, never what a param's value was DELIVERED as. A value that arrived as text and a value that arrived as data were indistinguishable to it.
- **Blast radius:** every task that passes a value into a step — a param carrying a path with a space, a command substitution, a shell metacharacter, or a lower-case name.
- **Root fix:** the environment is the second channel, and it is the SDK's channel, not a plugin-local one: `kit.RunnerConfig.StepEnv` + `kit.MergeStepEnv` (`opencharly/sdk#475`, released as `sdk v0.2026297.1851`). The plugin hands over the resolved map and lets the SDK own the merge rules; the plugin's own contribution is the clone before the stdin capture, because only the plugin knows that the map it hands over is about to be mutated with a runtime stream.
