# fix(git-submodules): continue the bump past a per-pin failure; give the maintenance gate its coherence control and a runner

## Summary

Three changes, one atomic phase, all in this repo's own scope:

1. **The `#13` fix — one per-pin failure no longer strands the rest of the walk.**
   `runGitSubmodules` mode `bump` returned at the FIRST failing path
   (`if st, msg := pinSubmodule(...); st != spec.StatusPass { return st, msg }`), so a
   single failing path skipped phase 2 entirely and left every pin sorted after it
   unmoved. It now RECORDS the failure, CONTINUES the walk, still derives the `pin_map`
   entries from the rolled `pinned_from`, and reports every failure together at the end.
2. **The gate repair (`#14`) — `scripts/check-coherence.sh`.** `scripts/gate-task.sh`
   builds a real charly with this candy compiled in through a local `-replace`, so the
   working tree's `sdk`/`spec` requires enter charly's module graph and MVS takes the
   max: a charly ref whose own pins LAG this module's raises `sdk`/`spec` past what
   charly's other compiled-in plugins were built against, and the build dies far from
   the cause. The control asserts that ordering BEFORE the build, and `--self-test`
   proves it can fail.
3. **CI gets two jobs.** `coherence` on every PR (seconds, the same control), and
   `gate` — the expensive live gate — on `main` and on demand.

**Provenance, because this is not a fresh branch by choice.** This is the rebased
successor of **#15**, taken over after its 60-minute floor expired with the owner
silent. #15's head cannot receive a fix commit: a rebase rewrites the branch, and R6
forbids a force-push, so the rebase lands on a fresh branch with a fresh thread and #15
is closed by a STATUS naming it. The three commits are #15's own, unmodified in content
and message; only the rebase's conflict on `scripts/gate-task.sh` was resolved, below.

## The RCA — what the abort cost, and why it is worth fixing in this repo

The umbrella's own `charly task sync` aborted on 2026-10-05, over this repository's

```

      task "pins" failed (1 step(s) failed)

```

Two defects compound there, and they are separate:

- **The reason was destroyed at the nested `task:` hop.** That is `#12`, closed by
  **#20** (`085f411`, merged 2026-10-05T19:02:54Z) — already in `main`, not in this diff.
  With #20 in, the failing path's own message reaches the top.
- **The walk stopped at the first failing path.** That is `#13`, and this PR is its fix.
  Its cost is not the abort line: phase 2 never ran, so **no `pin_map` entry was
  derived**, and the run left the superproject index half-staged. A session that
  committed at that moment would have violated policy B silently. One contended path
  was able to stall the whole pin operation.

## The fix, in detail

### 1. The walk continues (`candy/plugin-task/verbs.go`)

- A failing `pinSubmodule` appends to a `failures` slice and `continue`s. Every path is
  attempted; every failure is sorted and reported together:
  `bumped N submodule pin(s): ...; M FAILED: ...`. The verdict is still a FAILURE when
  anything failed — the walk continuing must not make a real failure look like success.
- **A new refusal, because continuing created a way to be silently wrong.** Once phase 1
  can fail a path and continue, a `pinned_from` that IS one of this project's own
  submodules may reach phase 2 having NOT rolled. Its gitlinks are then the OLD ones, and
  pinning `pin_map` entries from them is exactly the policy-B violation that the
  load-bearing order (charly rolls first) exists to prevent. `pinnedFromRolled` tracks
  it, and the refusal is REPORTED as a failure, never silent.
- **An EXTERNAL `pinned_from` (this gate's own `../src`) is read as it stands.** Only a
  `pinned_from` that is one of `paths` is rolled by phase 1, so only that case can be
  judged "did not roll"; an external one is never refused. This is the case the live gate
  drives, so a refusal here would have broken the gate's own fixture.

### 2. `scripts/check-coherence.sh` — one implementation, two callers (R3)

`gate-task.sh` runs it against the charly checkout it is about to build; the CI
`coherence` job runs it against charly `main`'s `go.mod` fetched over HTTP. Neither
carries its own copy. CalVer components are not zero-padded (`0.2026277.352` vs
`0.2026276.1822`), so the three dotted parts are compared numerically, never as strings.

`--self-test` proves the control can fail: leading passes, lagging fails, absent pin
fails.

### 3. CI: `coherence` everywhere, `gate` where the tree ships

The `coherence` job is seconds and runs on every PR — it is what catches, before merge,
the failure mode that let this gate rot unrunnable (#14). The `gate` job clones charly,
builds a real binary and drives the verbs on real git fixtures, so it runs on `main` and
on demand, not on every PR.
