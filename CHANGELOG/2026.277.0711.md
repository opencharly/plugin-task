The read is **gated on the plan itself** (`taskConsumesStdin`), not on stdin alone; see the RCA below. Truncation is bounded and recorded as a note. |

**RCA — the stdin read is gated, because an ungated one hangs.** `captureStdin` originally read whenever stdin was not a terminal. That read is bounded by **EOF alone**: an inherited OPEN pipe — a harness, `bash -c`, any parent that neither writes nor closes — never sends it, so `charly task` blocked **forever** where it previously returned at once (measured: `rc=124` against a writer left open, `rc=0` against `/dev/null`). A task that references neither var cannot observe the bytes, so not reading them is unobservable to it and removes the hang class entirely. `taskConsumesStdin` gates on the plan's **own** declaration and scans the **whole marshalled plan** rather than an enumerated field list: the walk expands `${NAME}` over every string field of every step (`kit.ExpandOpVars`), and restating that field list here would be a second copy of it to drift (R3). `TestTaskConsumesStdin_GatesTheRead` drives the gate against a pipe whose writer is **never closed** — an ungated read blocks there, so the test completing at all is the assertion.

**Integration note — origin/main moved under this branch.** `feat(prune): add verb:prune` (`plugin-task#7`) merged after this branch was cut and touched the same files. It was **merged in, not rebased**; there were no conflicts. This branch is **6 commits ahead of `origin/main` (`fab7c28`) and 0 behind**, verified by `git fetch origin main` then `git log --oneline origin/main..HEAD` / `HEAD..origin/main` (the latter empty).

**Consumer obligation, stated because it is invisible in the diff:** the lobster engine's lowering emits `charly … task … --output` and pipes `stdin:` in; both flags are new here, so a consumer must require a `plugin-task` at or after this tag. The lowering itself rides `sdk` (sdk's `workflowkit.Lower`), not this repo.

### The overlay, stated because it is what makes this run possible

The bed needs a charly that compiles this plugin in, and the pin that would do that can only adopt a tag that does not exist until this merges. So the binary is built the documented Go-`replace` way — the mechanism `/charly-check:check`'s `beds-and-r10.md` names as the *"Go-`replace`-style 'verify before you push'"* dev-tree override:

```
go build -o ./bin/charly \
  -ldflags "-X main.BuildCalVer=$(bash scripts/calver.sh)" \
  -replace github.com/opencharly/plugin-task/candy/plugin-task=<worktree>/candy/plugin-task \
  -replace github.com/opencharly/plugin-command/candy/plugin-command=<worktree>/candy/plugin-command \
  ./charly
```

`go.mod`/`go.sum` are snapshotted before the build and restored after it, so the worktree is clean and carries no replace directive. `plugin-command` is compiled in (`charly.yml`, `compiled_plugins:`), so this bed takes the **in-proc** dispatch path and compiles the changed producer in; `plugin-task` likewise.

**The bed does not run green against `origin/main`'s pins, and the body states that rather than implying otherwise.** What is red without the siblings is the **8-step** bed — and 6 of those 8 steps are added to it by the *charly* leg of this wave, not by this PR. `charly`'s `main` today carries a 2-step `check-task` (`task-list-declared`, `task-verb-runs`) that touches neither `--output` nor stdin. So this PR's own merge point reddens **no existing gate** — but that also means **no existing gate certifies this surface yet**. That asymmetry is the whole of the tier reasoning below, and it is why §5 names the overlay explicitly instead of implying the run stands on `origin/main`.
