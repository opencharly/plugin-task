# 2026.297.1509 — feat(task): give the task summary its third bucket — a step that ran nothing

Closes #35

## Summary

`charly task` counts **steps** and **failures**. A step that ran nothing is neither: it is not a failure, so it is counted among the N steps, and it is not disclosed. A green task line can therefore read "26 step(s), 0 failed" over a run in which six comparisons never happened. The org already owns the vocabulary for exactly this state — `sdk.CheckSkippedExitCode = 3` ("the phase RAN NOTHING — neither a pass nor a failure") — and the check runner honours it. The task runner had no equivalent.

This PR gives the task runner the third bucket.

**What the summary says now.**

- The headline is `task %s: %d step(s), %d failed, %d skipped`.
- The hop's aggregate is `ran %d task(s), %d step(s) failed, %d skipped`, and it is KEPT as the PREFIX whenever a step ran nothing. It used to be dropped when the nested run had step messages and no failures — which is exactly the shape a run with skips has — so the count of what did not run was the thing the summary threw away.
- The JSON report carries `"skipped"`.
- The nested failure verdict carries the count too, so a reader of a failure also learns what did not run.

**The silent path keeps its meaning.** `silent: true` still suppresses the per-step output. A skipped step is not output to suppress: it is a step that never ran, and its reason is the only thing that says why. A silent task that hid it would report a count with no cause — the reading this bucket exists to end. So the silent path discloses the SKIPPED steps' lines, and nothing else.

**The exit status is untouched.** A step that ran nothing is not a failure, so the run still exits 0. That is the honest reading: R8's sanctioned skip stays non-fatal, and the honesty comes from the disclosure, not from turning a skip into a red.

**The other half of the issue — the `command:` verb's own channel — landed in opencharly/plugin-command#11** (merged, tagged `v2026.297.1448`): a `command:` step that declares `skip_exit: 3` is SKIPPED rather than failed. It is **OPT-IN**, and that is an explicit deviation from this issue's unconditional wording ("a `command:` step exiting 3 becomes a SKIPPED step"): an undeclared exit 3 stays an ordinary failure, because the exit code belongs to the step's AUTHOR, and reading an uninterpreted 3 as a skip would turn a real failure into a non-failure. This repo counts the skip the channel produces, whichever way it was minted.

**The third part of the issue — telling a legitimate skip (an absent credential) from a coverage hole (an absent submodule) — cannot be owned here.** The org has no typed skip reason: every skip is a `StatusSkip` plus a free-form sentence, and `spec.CheckResult` carries no field for a classification. A string-match over the SDK's sentences in this repo would be a second copy of another module's vocabulary. It is filed as **opencharly/sdk#472** with its RCA.
