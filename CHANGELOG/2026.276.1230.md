# 2026.276.1230 — fix(git-submodules)!: refuse an uninitialized submodule — never let git -C walk up to the superproject (charly#768)

## Summary

`charly task sync` (and the `charly task pins --param MODE=bump` it composes)
could detach the caller's **umbrella worktree**: the session's `feat/` branch was
silently replaced by a detached HEAD at `origin/main`, mid-sync, leaving the
staged gitlinks uncommitted. Closes charly#768.

**Root cause (RCA).** `verb:git-submodules`' `bump` called
`pinSubmodule(projDir, path, ref)`, which ran

```
git -C <path> switch --quiet --detach <ref>
```

`git -C <dir>` only *changes directory* — it does not pin the repository. For a
submodule directory that is **present but uninitialized** (an empty dir, or one
whose `.git` is absent — exactly the state of a freshly-created worktree that ran
`git worktree add` without `git submodule update --init`), `git -C <dir>` **walks
up** to the enclosing repository and resolves to the **superproject**. So
`git -C <empty-submodule-dir> switch --detach origin/main` switched the umbrella.

**Fix (structural, not a guard on top of the bug).** A new `submoduleAt(projDir,
path)` resolves an initialized submodule checkout and returns the walk-up-safe

```
git --git-dir=<abs>/.git --work-tree=<abs> …
```

form, which resolves to **nothing** (exit 128) for a stray directory — it can never
resolve to the parent. It **fails loud** when `<path>/.git` is absent, naming the
path (`pinSubmodule`, the `status` reads, and the `pinned_from` gitlink reads — one
shared `submoduleGitlink` helper — all go through it). The `git add` of the gitlink
stays a separate superproject invocation, which is correct: the gitlink is staged in
the superproject.

**The walk-up form is removed, not merely guarded (R5).** The `git -C <submodule-path>`
form is gone from the live code; the only remaining textual `git -C` occurrences are
comments recording the bug (see the R5 row below).
