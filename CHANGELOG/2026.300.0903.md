# 2026.300.0903 — fix(git-submodules): the bump report counts the pins that MOVED, not the index WRITES (plugin-task#53)

## Summary

The `git-submodules` verb's `bump` mode reported how many pins it **TOUCHED**, in a wording that read as how many pins **MOVED**. Every path the walk visits is WRITTEN — the walk must record where a pin is even when the answer is *"where it already was"* — so a bump over an already-current tree reported the same number as a bump that advanced every pin. Measured in the umbrella's pin wave 9 on 2026-10-24 (opencharly/opencharly#684, landed as opencharly/opencharly#685) and recorded in opencharly/plugin-task#53: **406 pins written, 4 pins moved**.

**What changes.** The report now carries TWO numbers per group — how many pins the group TOUCHED and how many of them MOVED — and the three groups are a **PARTITION** of the paths the walk touched, so the three moved counts SUM to the moved total:

```
pinned N pin_map entr(y|ies) (names; E moved) after rolling M leaf submodule(s) to their default-branch HEAD (R moved) and advancing K leaf pin(s) in the index (I moved); T pin(s) moved
```

The two leaf clauses count LEAF pins and the `pin_map` clause counts the EDGES — the plugin's own vocabulary, which the currency report already uses (*"upstream leaf/leaves"*, *"derived-from edge(s)"*). The FAIL report carries the same two numbers per group, so a failed wave says what it moved and what it only touched.

**The mechanism.** `advancePinInIndex` records a pin with `git update-index --add --cacheinfo` and returns PASS on exit 0, and the caller counted every PASS. The fix reads the index's recorded gitlink **before** the write and compares it with the value the write records: every branch records exactly the new sha (an index write, or a roll staged onto a checkout that now sits at that sha), so one comparison answers whether the pin MOVED. A `pin_map` entry is counted in the EDGE group and not in the index-advance group, so the groups stay disjoint and the sum is the truth — an edge is never counted twice.

**The control.** The SAME tree bumped TWICE: the walk writes the pin both times, so the touched count is identical and only the moved count can fall to zero. That is the only comparison that discriminates a write count from a move count, and it is the test's second step.

The RCA of the finding is opencharly/plugin-task#53 (mechanism, missed control, blast radius, root fix). The missed control was mechanical: nothing compared the report's number with the gitlinks the bump actually changed, so the shape was asserted and the meaning was never tested. The blast radius is every reader of the bump report — the umbrella's wave PRs quote it — and the umbrella's `scripts/sync-pr-body.sh` fixture, which reproduces this exact shape (that consumer is filed below).

Closes #53.
