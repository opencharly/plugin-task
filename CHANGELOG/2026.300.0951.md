# 2026.300.0951 — test(git-submodules): the moved counters are HELD, one test per counter

## Summary

The `git-submodules` verb's `bump` report separates the pins it **WROTE** from the pins that **MOVED** (opencharly/plugin-task#53, landed as opencharly/plugin-task#58). Its coverage proved **one of the three** moved counters, and one of the report's two arrangements.

**What #58's coverage reached.** The merged fixture declared a path with **no checkout**, so the walk advanced it in the index and `indexMoved` was the only counter that could rise. The other two were correct by inspection and unasserted:

| counter | group | what it counts | covered before |
|---|---|---|---|
| `rolledMoved` | `done` | phase-1 paths **with** a checkout, rolled onto their default-branch HEAD | **no** |
| `indexMoved` | `inIndex` | phase-1 paths with **no** checkout, advanced in the index | yes |
| `pinnedMoved` | `pinned` | the `pin_map` entries — the EDGES | **no** |

**The gap this PR closes.** Three, and the third is the one #58's own body made a claim about:

1. **The materialised roll.** A path with a checkout is rolled by `pinSubmodule`, which stages the checkout's new HEAD onto the index. The moved count is read from the index before and after the roll, and the two can differ for a reason the unmaterialised path never exercises: the roll moves a CHECKOUT, and the index write records what that checkout now holds. A regression that compared the wrong value here would report a roll that did not happen, or a move that did.
2. **The `pin_map` edge, counted ONCE.** #58 removed a double-count — a `pin_map` entry used to be appended to `inIndex` **and** to `pinned`, so an unmaterialised edge was counted in two groups. The fix counts it in the EDGE group only, and "one `pin_map` entry that is no longer counted twice" is exactly the claim with no test behind it. A regression that restored the `inIndex = append(inIndex, upath)` line would leave every existing test green.
3. **The FAILURE report.** The same three counters are printed in the FAIL report in a **different arrangement** — *"rolled … ; advanced …; pinned …"* instead of *"after rolling … and advancing …"*, and the pin_map clause prints its count alone instead of names-then-count. Nothing asserted them there, so a regression in the failure report's numbers would reach the product silently — and the reader of a failed wave is the reader who most needs to know what the wave moved before it failed.

**What lands.** Four tests, in one new test file, and **no product change**:

- **the ROLL counter** — a materialised submodule pinned one commit behind its origin's `main`, bumped twice: the touched count is identical and only the moved count can fall to zero.
- **the EDGE counter, and the partition it exists for** — the umbrella's own shape in miniature: a source whose tree records a nested gitlink, an umbrella that declares it as a submodule, and an **unmaterialised** path the edge derives from that nested pin. The edge is counted **once**, in the edge clause, and not in the index-advance clause; the three moved counters **sum** to the moved total.
- **the SUM** — the three groups partition the paths the walk touched, so their moved counts add up to the moved total. Asserted on the REPORT, not on the internal counters: a report whose numbers do not add up is a report a reader cannot trust. Its fixture is built so the sum is **observable** — the walk TOUCHED two paths (a materialised submodule rolled onto its tip, and a declared path with no checkout whose pin is already current) and MOVED one, so a report that counted writes instead of moves prints a different number in the index clause and the four printed numbers stop adding up.
- **the FAILURE report** — the same three counters in the other arrangement, with a **non-zero** moved count (a fail report whose counters were all zero would be satisfied by a report that printed a hardcoded `0`, so it would prove presence and not correctness).

**The RCA** is opencharly/plugin-task#59 (mechanism, missed control, blast radius, root fix), filed and CLAIMED by this session. The missed control was mechanical: the coverage was written per **DEFECT** rather than per **COUNTER**, and the one discrimination the defect needed — the same tree bumped twice — is silent about the other two write paths. The blast radius is every reader of the bump report: the umbrella's wave PRs quote it verbatim.

The finding was raised on this repo's own PR #58, as the review's note 2 ("partial branch coverage"). A finding raised on your own PR is **fixed, not filed away** — so it is fixed here, in the test file that owns it, and #58's thread links this PR.

**Round 2 — the validator's finding on this PR, and what it changed.** The org `charly/pr-validator` BLOCKed round 1 on one thing, and it was right: the R7 evidence said each mutant turns *exactly* the matching test red and leaves the other three green, and that had been measured with a targeted `-run` filter — so the isolation was **asserted and never observed**, and it is **false**. The roll mutant also zeroes the report's moved **total**, so the SUM test, the EDGE test and the FAILURE test go red with it. Round 2 (this PR's second commit) fixes it in three parts: the mutant runs now execute the **whole package's suite** and the body pastes the complete failing set of each mutant, measured rather than claimed; the claim is corrected to what the output shows; and the SUM test gets the fixture described above, so the **relation** has a failure mode of its own — a sixth mutant that reports the pins the index group **touched** instead of the ones it **moved** breaks the sum and is caught by no other test in this file. The RCA is in the **Rulebook compliance** section and on the PR thread.

Closes #59.
