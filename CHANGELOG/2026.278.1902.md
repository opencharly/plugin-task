# fix(task): carry a failing step's own message across the nested `task:` hop

## Summary

A composite task — a `task:` step wrapping another task — reported only the nested task's aggregate verdict, `N step(s) failed`, and **dropped the failing step's own message**. The leaf's reason exists (the top-level reporter prints every step), and it was destroyed exactly at the nested hop, so a composite failed with no path and no reason.

MEASURED, the issue's own minimal reproduction, driven live:

```
$ charly task --dir=/tmp/probe leaf            # the leaf, run directly — the reason is right there
task leaf: 1 step(s), 1 failed
  [fail] run — the leaf step (its Message is the reason)
      exit=3, want 0 (stderr: leaf-reason: boom on stderr)

$ charly task --dir=/tmp/probe probe           # one nested hop up — the reason is GONE (pre-fix)
task probe: 1 step(s), 1 failed
  [fail] run — the outer step (a nested task step)
      task "leaf" failed (1 step(s) failed)
```

**Hit for real:** the umbrella's `sync` → `task: pins` → `git-submodules: mode bump` over ~424 submodules failed this way; the cause was transient, and because the reason was dropped it is now **unknowable** which fetch/switch failed or why. Re-running the identical command on the identical tree later succeeded. That is the R1 "root-cause every anomaly" failure mode: the harness itself made the anomaly un-diagnosable.

### Where it was lost — the hop, and ONLY the hop

- `cli.go` returned `verbResult(spec.StatusFail, fmt.Sprintf("task %q failed (%s)", n, r.Message))` and dropped `r.Steps`. The single `CheckResult` it builds has **no field for nested steps**, so the task-level Message is the only carrier across the boundary.
- **`runner.go`'s flattening (`res.Message = "%d step(s) failed"`) is NOT the defect.** The top level already prints every step line (`printResultText`) and `printResultsJSON` already emits the `steps` array, so enriching it there would **DUPLICATE** the reason rather than carry it. I implemented it in `runner.go` first and **reverted it** (`git checkout -- runner.go`) after reading the callers. The fix belongs at the hop and nowhere else.

### The fix

- **`nestedVerdict(name, r)`** is extracted as the named seam the hop's loop **actually calls**, returning `(status, message)`; a non-pass stops the walk. It exists as a named function specifically so a test can drive the real path.
- **`nestedFailureMessage(r)`** renders each FAILING step as `[status] keyword — text` followed by its own `Message`, indented, mirroring `formatStepLine` so the nested text reads the same as the direct run's. Passing steps are not listed.
- The **hard-error arm is unchanged**: a task that aborted has no step results to carry, so it keeps its own task-level Message.

### The live gate now exercises the changed path (validator findings 1–3)

`scripts/gate-task.sh` gains **section 1b**: a `leafreason` task whose failing step writes a reason, and a `composite` task nesting it behind ONE `task:` step. It asserts (a) the leaf, run directly, shows its own reason; (b) the COMPOSITE exits non-zero; (c) the composite's verdict **carries the leaf step's own reason across the hop**; (d) it names the failing step's **PATH**, not just the reason. It then **prints** the live verdict, so the proof is in the gate's own output:

```
== verb:task nested hop (a composite must carry the leaf step's own reason) ==
   | task composite: 1 step(s), 1 failed
   |   [fail] run — the outer step (a nested task step)
   |       task "leafreason" failed (1 step(s) failed
   |         [fail] run — the leaf step (its Message is the reason)
   |             exit=3, want 0 (stderr: leaf-reason: boom on stderr))

```
