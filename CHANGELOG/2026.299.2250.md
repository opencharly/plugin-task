# 2026.299.2250 — fix(git-submodules): a bump that would drop a nested checkout's work refuses (plugin-task#54)

## Summary

`charly task sync` (the `verb:git-submodules` bump) rolls a materialized path and then reconciles that path's OWN nested checkouts with `git submodule update --recursive`. That update moves a nested checkout onto the gitlink the parent records, and it does not ask: when the nested checkout's HEAD carries a commit that NO branch, tag or remote-tracking ref holds, the update takes the checkout off that commit, exits 0, reports nothing, and leaves the operator's commit in the reflog alone.

**This PR makes the bump REFUSE that move** — naming the nested checkout, the commit and the recorded pin — and it refuses BEFORE anything moves, so **the refused submodule** is left exactly as it was: its own checkout is not switched, its pin is not staged, and the nested checkout still holds the operator's commit. The refusal is PER-SUBMODULE, not a whole-bump abort — the walk collects a failed path and continues — and the correction at the end of this entry states the measured scope (opencharly/plugin-task#56).

**THE MEASUREMENT** — four shapes, git 2.56, a real umbrella → outer → inner fixture over `file://` remotes:

| nested checkout at | the update | the local commit |
|---|---|---|
| the recorded pin, behind | exit 0 | nothing to lose |
| the recorded pin + a commit on a branch | exit 0 | kept by that branch |
| the recorded pin + an ORPHAN commit | exit 0 | DROPPED, reported by nothing |
| the recorded pin + a dirty file | exit 1 | git refuses, loudly |

So the loss is the update's blind spot, not git's doing: the same update refuses a DIRTY nested checkout loudly, and a branch keeps its commit across the move. The rule that follows is local and needs no fetch — a nested checkout may be moved when the commit it is at will still be reachable: when the move goes FORWARD onto it (`merge-base --is-ancestor`), or when a ref in that checkout still contains it (`for-each-ref --contains`).

**THE FIX.** Before the switch and before the pin is staged, the nested checkouts are judged. A refusal stops THAT SUBMODULE with its tree untouched: the nested checkout still holds the operator's commit, the superproject's pin was not staged, and the submodule's own checkout was not moved. The fetch and the switch are two commands for exactly that reason. What the refusal does NOT do is stop the walk: a failed path is collected and the walk continues (opencharly/plugin-task#13), so a path that sorts earlier is already rolled and staged when the refusal is reported — the correction below states the measured scope.

The judgement reads the gitlinks the TARGET commit records, and falls back to the checkout's own `.gitmodules` only when that tree cannot be read here — a tree that records no submodule is a fact about the tree, and a tree that cannot be read is a different fact.

The reader of a `.gitmodules` is now `gitmodulesPaths(dir)`: the same reader serves the project's own `.gitmodules` and the one a submodule declares for its own nested checkouts, so there is one reader and one shape. The old name is gone in the same cut, and the live sweep is in **How tested** below.

Closes #54.

## Correction — the refusal's scope is the REFUSED SUBMODULE (opencharly/plugin-task#56)

This entry first said the refusal "leaves the tree exactly as it was" and "stops the whole bump with the tree untouched". The product's contract is **per-submodule**: `bump` collects a per-path failure and CONTINUES (opencharly/plugin-task#13 — "ONE path's per-invocation failure costs that ONE pin, not every pin sorted after it", proven by `TestGitSubmodules_BumpContinuesPastFailure`), so a path that sorts earlier has already been rolled and its pin staged by the time the refusal is reported.

**The measurement** — an umbrella that pins two submodules, the paths SORTED, so `aaa-leaf` is rolled FIRST and `outer` (the one whose nested checkout carries the operator's commit) is refused SECOND:

```
bump: fail: 1 pin(s) FAILED: the nested checkout outer/inner carries a commit the update would drop — its HEAD c816a42e78bbec10ca29bf4306afa7a05d6ffd50 is in no branch, tag or remote-tracking ref of that checkout (the recorded pin is 1ee4571b7ca0263f7acc309da9983d135bb093d9), so the update would move it off that commit and leave it in the reflog alone; push it, branch it, or stash it, then re-run; rolled 1 submodule(s) to their default-branch HEAD; advanced 0 pin(s) in the index; pinned 0 pin_map entr(y|ies):
```

`rolled 1 submodule(s)` and one refusal: the sibling was rolled and its pin staged, and the refusal stopped the OTHER submodule. The tree was not untouched — the REFUSED SUBMODULE was.

**What is corrected, and what is not.** The refusal PRESERVES the work and NAMES the nested checkout that carries it, exactly as this entry's own measurement shows; that is unchanged. What was wrong is the SCOPE of the sentence around it — in this record, in the code comments that describe the refusal (`candy/plugin-task/verbs.go`, `pinSubmodule` and `judgeNestedLevel`), and in the #54 gate's fixture, which carried ONE submodule, so the scope was never observable.

**The control that now holds the scope.** The #54 fixture carries a SIBLING that sorts first, and `TestGitSubmodules_BumpRefusalIsScopedToTheRefusedSubmodule` asserts the scope in both directions at once: the refused submodule's pin is not staged, its checkout is not switched and the nested checkout still holds the operator's commit, while the sibling's pin advances to the origin's tip. The test FAILS on the pre-#54 sources — the bump PASSes, both submodules roll, and the nested work is dropped — and PASSes on the fixed tree.
